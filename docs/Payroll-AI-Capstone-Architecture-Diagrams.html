1. System overview

The application is four independently running parts. The browser talks to each backend service directly. Sign-in is owned by employee-service; it issues a signed JWT. The other two services keep no user accounts and need no call to check it: each verifies the signature itself with a secret (JWT_SECRET) shared by all three.

2. employee-service (Java, Spring Boot)

Two halves share one database: the employee directory and the sign-in office. A doorman (AuthInterceptor) guards only the employee URLs; the /api/auth URLs stay open so people can sign in.

Why it is built this way

ChoiceReason
Passwords stored as salted hashesA leaked database does not reveal passwords. Each user gets a different salt, so identical passwords look different.
Signed JWT instead of a stored tokenOther services can verify it with the shared secret, with no lookup and no call. The signature stops anyone changing the role. The cost: it cannot be cancelled before it expires.
Refuses to start without JWT_SECRETA missing or short secret would let anyone forge an admin token, so the service fails loudly at start-up.
Unknown e-mail still runs a hash checkResponse time then does not reveal which e-mails have accounts.
Format rules as annotations on the DTOEach rule sits next to the field it protects. Rules that need other data stay in the service.
Rules repeated as database constraintsA second line of defence; also makes the unique e-mail safe when two requests arrive at once.

The service stores nothing. For the chat it fetches the data itself, using the user's own token, so the chat can only see what that user can already see.

5. Data model

Three tables live in the H2 database (employees, users, password_resets). The sign-in token is a JWT and is stored nowhere. Payroll runs and photos live elsewhere and point at employees by value, not by foreign key. Accounts (users) are deliberately separate from employees: signing up does not create an employee.

Consequence of the in-memory database. Employee ids restart at 1 whenever employee-service restarts, while saved payroll runs and S3 photos keep the old ids. After a restart an old run or photo can point at a different person. A persistent database with stable ids removes this risk.

6.4 Forgot password

#StepWhat happens
1Request a codePOST /api/auth/forgot-password. The answer is the same message whether or not the account exists.
2Code createdIf the account exists: a random 6-digit code valid 15 minutes; only its fingerprint is stored. No e-mail service exists, so the code is written to the employee-service log.
3ResetPOST /api/auth/reset-password with e-mail, code and new password (8 to 100 characters). The code is compared in constant time; wrong guesses count toward the same 5-failure lock-out.
4AftermathNew hash saved and code deleted (single use). Tokens already issued are not cancelled: a JWT is not stored, so they keep working until they expire (up to 60 minutes).

9. Resilience: what happens when something fails

FailureBehaviour
employee-service downNobody can sign in. Salary lookups, the employee list and photo checks fail (502). Users who already hold a valid JWT can still reach payroll history and the AI review, because those services verify the token themselves.
JWT_SECRET missing, short or differentMissing or under 32 characters: that service refuses to start and says why. Different between services: sign-in works but the other service answers 401 to every call.
payroll-service downPayroll, history and photos fail. Chat still answers about employees and says payroll runs are unavailable.
ai-service downReview and chat fail with an error. Employees, payroll and photos are unaffected.
OpenAI down or key invalidReview returns the fixed-rule results and says the AI check was unavailable. Chat returns 502 or 503.
AWS off or failingPhotos show as initials; upload returns 503. The cause is logged as "Image storage failed". Payroll is unaffected.
Token expires, is forged or tampered withThe next call answers 401 and the app returns to the sign-in screen.
Process crashes during a payroll saveThe JSON file is never left half-written (temp file then rename).
Restart of employee-serviceSign-up accounts, reset codes and lock-out counters are lost. Only the seeded admin returns. Employees reset to the 10 samples. Tokens already issued still work until they expire, even for accounts that no longer exist.

10. Known gaps and improvement path

GapImprovement
Accounts and employees are in memory; ids restartMove to a persistent database (for example PostgreSQL) with stable ids and foreign keys; move payroll runs into it too.
Seeded admin password is admin, shorter than the 8-character minimumRequire a strong password for the first administrator; change it before real use.
Reset code is written to a logSend it by e-mail; confirm e-mail addresses at sign-up (sign-up is open to any @pwc.com address today).
Plain HTTPHTTPS in front of every service, ideally behind one gateway that also adds rate limiting.
A JWT cannot be cancelled before it expires (60 minutes)Sign-out, password reset and role changes do not affect tokens already issued. Add a short list of revoked tokens that every service checks, or use refresh tokens with a much shorter lifetime.
One shared secret signs and verifies tokens, and sits in three placesAny service holding it can forge an admin token. Use a secrets manager, and switch to asymmetric signing (RS256) so only employee-service can sign.
Chat sends personal details to OpenAIRemove names, e-mails and phone numbers before sending, or offer an offline option.
Almost no automated testsUnit tests for validation and tax maths, API tests per service, tests that the chat refuses off-topic questions, a UI smoke test.
Tax and contribution rates are demonstration valuesMake the tables configurable with effective dates, and verify them with SSS, PhilHealth, Pag-IBIG and the BIR.
